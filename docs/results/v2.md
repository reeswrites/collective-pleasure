Status: instrument calibration only. Nothing here is a research result about convergence. Predictions: docs/results/v2-prereg.md (committed at d94ffb2, before any V2 code ran, not edited since).

Run: `uv run python scripts/v2_run.py` and `uv run pytest`. Mock agents only; no LLM, no network at run time, no GovSim.

## The deviation from the prereg, stated plainly

Prediction 3 described P1 as "month_total + catch <= 40". First run, as preregistered in spirit: the card written as the single condition `month_total + catch > 40` FAILED check (b) no-deadlock (and (d) repair path): in a state already over 40 this card forbids even catch 0, so no action is permitted. The solver was right and it is a genuine bug in the patch card, not in the checker. Fix: add `catch > 0` to the card's conditions (same intended rule). The prediction text was not changed; the first-run failure is recorded in docs/negative-results.md and a regression test (`test_naive_cap_without_catch_gt_zero_is_a_deadlock`) keeps it.

## ASSUMED choices

- In-repo fishery harness instead of GovSim (ADR 0003); up to 12 sub-rounds per month, agents interleave within a sub-round (needed so a month cap is shared fairly, not first-come).
- Meaning of `conditions`: must_not violated when all predicates hold; must violated unless all hold; may adds no constraint.
- Gate reasons are the violated card ids (by Z3 evaluation), not an unsat core. Patch-check witnesses use a deletion-based minimal core.
- Sanctions are declared and checked but not enforced by the harness in V2. `cap_halve` is modelled as catch <= 5 and `suspend` as catch = 0 for the repair-path check. A card declared with a sanction counts as repairable if some action stays permitted in every state within bounds and the sanction ends within k.
- Check (a) tests must / must_not pairs on the same aim only (not must vs must). Check (d) is "open" when a sanction lasts longer than k months.
- Oracle starvation requires another agent catching in the same months; collapse is measured after regrowth. Gini threshold 0.4 frozen in the prereg.
- Miner: infers a per-month cap only from rejections that the per-action range and the pool cannot explain; no such rejection means "no cap". State machine: states = pool bucket (<20, 20 to 59, 60+) x month-total phase (0, 1 to 39, 40+), edges = permitted action classes (negative, zero, 1 to 5, 6 to 10, over 10). De jure machine is computed from the gate over a coarse state grid (step 5).
- Patch card P1 uses a constant cap of 40, scripted; the scripted patcher reads only the failing trace and current cards.

## Surprises

See docs/surprises.md (2026-11-10 V2 entries): the naive cap card deadlocks; explorer coverage of the state machine is thin under the patched spec; exploiters are partly stopped by the pool-bound card F2, not by the cap.

## What this does and does not show

The four instruments (gate, oracle, patch checks, miner) behave as designed on a fixture where the answer is known. It says nothing about whether refinement converges, about LLM agents, or about seams a human did not plant. The miner and the cap detection are tuned to this fixture's rule shapes.
